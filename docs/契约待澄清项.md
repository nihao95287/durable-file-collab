流程：确认人在 PR 下回复 -> 把「状态」改为**已定** -> 删掉 `docs/Interfaces.md` §8 里的「待 P2、P4 确认」-> 第 1 周打 `contract-v1` tag。

| 编号 | 问题 | 决议 | 契约位置 | 状态 |
|---|---|---|---|---|
| 1 | `claim` 把 `queued` 列为可认领，但没有任何 `queued -> transferring` 的流转，worker 可以直接绕过「接收方确认」 | `queued` **不再可被认领**；新增流转 `queued --dispatch_immediate--> transferring`（P1 分流，用于无需接收方确认的任务如 `version_upload`）；`claim` 只认领 `transferring` / `network_wait` | §1.2 规则 5、§2.2 | 已定（P1），待 P2/P4 知悉 |
| 2 | daemon 分流需要「接收方是否在线」，但 `users` 是 P2 的表，P1 不许跨模块读表 | P2 启动时调用 `set_online_probe(fn)` 注入查询；未注入时一律按离线分流，任务停在 `waiting_online`，等 P2 心跳接口调用 `wake_user` | §2.6、§2.2 | 待 P2 确认 |
| 3 | `nack` 签名是 `-> None`，契约却要求超限时「抛 `RetryExhausted`」 | 保留抛异常，但明确**先提交 `failed` 状态、再抛**；调用方（P4 worker）必须捕获并区分「任务失败终态」与「自身崩溃」 | §2.3 | 待 P4 确认 |
| 4 | `delivery_tasks` 能不能从 `payload` 提取字段 | 只冗余 `sender_id` / `receiver_id` / `size_bytes` 三列（可空），其余字段原样存 JSON，P1 不解释业务含义 | §2.1 | 待 P2/P3 确认命名 |
| 5 | 分片大小归谁、`task_chunks.checksum` 谁来填 | 分片大小是 P1 配置（`chunk_size_bytes`，默认 1 MiB）；`size_bytes` 缺失按单分片；`checksum` 是**该分片的基准校验值**，入队时未知，由首次 `ack_chunk` 写入，重复 ack 必须与之一致；分片校验值计算归 P4 worker | §2.1、§2.3 | 待 P4 确认 |
| 6 | 「延迟接收」要同时写状态和 `next_run_at`，而 `transition()` 没有该参数 | 新增补充入口 `set_delay(task_id, delay_until, actor)`，在**同一事务**里完成 `waiting_confirm --delay--> delayed` 与到期时间写入；到期由 `recover()` 用 `delay_expired` 唤醒 | §2.4b | 待 P2 确认（调用方） |
| 7 | 状态流转要不要写审计、和 `task_events` 什么关系 | P1 通过 `audit.join_tx(tx)` 写 `task.enqueued` / `task.transition` / `chunk.acked` / `task.retry_exhausted`；`task_events` 继续保留（崩溃恢复依据），审计表给管理员查询；审计库交付前 P1 接受注入 `None`/`NullAuditSink` | §3 | 待 P4 确认 |

## PR 描述（可直接粘贴）

> **标题**：`docs: contract-v1 修订提案（P1 队列内核实现时发现）`
>
> **背景**：实现 `QueueAPI` 骨架时发现 7 处契约歧义，已在 `docs/Interfaces.md` 落成明确答案，P1 侧代码与测试同步完成（`src/storage/`、`src/common/audit.py`）。其中第 1、6 条已由 P1 定稿，**下面 6 条需要各位确认**：请直接在对应条目下回复「同意」或「反对 + 理由」。
>
> **1. P2 —— `queued` 任务的分流需要「接收方是否在线」**（契约 §2.6 `set_online_probe`）
> - 现状：P1 提供 `set_online_probe(fn)`；不注入时一律按离线分流，任务停在 `waiting_online`，等 `POST /sessions/heartbeat` 调 `wake_user` 唤醒。
> - 你要做的：进程启动时调用一次 `queue.set_online_probe(...)`（约 1 行）。
> - 否回的代价：改由心跳主动推进任务 → 改 `Queue.dispatch_pending` 与契约 §2.2/§2.6，并补测试。
>
> **2. P2 —— 延迟接收入口**（契约 §2.4b `set_delay`）
> - 现状：新增 `set_delay(task_id, delay_until, actor)`，把 `waiting_confirm --delay--> delayed` 与 `next_run_at = delay_until` 写进同一事务。
> - 你要做的：`POST /deliveries/{id}/decision` 的 `delay` 分支调用它，不要自己改状态或 `next_run_at`。
> - 否回的代价：改 `set_delay`/`transition` 形参 + §2.4b + 对应契约测试。
>
> **3. P4 —— `nack` 超限时的异常语义**（契约 §2.3）
> - 现状：保持 `nack(...) -> None`，但**先提交 `failed` 状态、再抛 `RetryExhausted`**。
> - 你要做的：worker 捕获 `RetryExhausted` 并当成任务终态，别让它冒泡成 worker 崩溃。
> - 否回的代价：改成返回状态/布尔 → 改 `nack` 签名 + C-02/C-09 测试 + §2.3。
>
> **4. P2、P3 —— `delivery_tasks` 只从 payload 冗余 3 列**（契约 §2.1）
> - 现状：只提取 `sender_id`、`receiver_id`、`size_bytes`（均可空），其余字段原样存 JSON。
> - 你要做的：确认这三个键的命名与语义（`version_upload` 无 `receiver_id`，会存 NULL）。本条无需写代码。
> - 否回的代价：改 `db/schema.sql` + `enqueue_task` + 迁移脚本；新增列还要动 C-10。
>
> **5. P4 —— 分片大小与 `task_chunks.checksum` 语义**（契约 §2.1、§2.3）
> - 现状：分片大小是 P1 配置（默认 1 MiB）；`checksum` 是该分片的**基准校验值**，入队时未知，由首次 `ack_chunk` 写入，重复 ack 必须一致。
> - 你要做的：worker 对每片单独计算校验值并传给 `ack_chunk`；用 `heartbeat_claim` 续期，别让可见性超时把任务抢走。
> - 否回的代价：若要求「入队时就带每片校验值」→ 同时改 §2.1 payload 约定、`enqueue_task` 与 P2 的提交逻辑。
>
> **6. P4 —— 审计接口形状**（契约 §3）
> - 现状：P1 按 `audit.write(event_type, actor_id, target_type, target_id, detail)` 与 `audit.join_tx(tx) -> writer` 接线（声明见 `src/common/audit.py`），写 `task.enqueued` / `task.transition` / `chunk.acked` / `task.retry_exhausted`，与业务同事务。
> - 你要做的：让 `src/audit/` 提供这两个函数即可，P1 侧无需改动。
> - 否回的代价：改 `src/common/audit.py` + `src/storage/events.py` + 测试替身。
>
