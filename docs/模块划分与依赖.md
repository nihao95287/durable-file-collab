## 0 使用方式

1. 组员在 [§6 认领表](#6-模块认领表) 里挑选模块（可一次认领多个），把「认领人 / 状态」改成自己，然后按 [§3 依赖关系](#3-依赖关系详细) 的顺序开发。
2. **模块 ID（`M01`～`M15`）是稳定标识**：用在分支名、PR 标题、CODEOWNERS 和任务看板上，例如 `feat(M08): base_version 冲突检测`。
3. 模块之间的依赖只允许通过 [§4 边界规则](#4-模块边界与解耦规则) 允许的接口发生；文档没写清的依赖即为「违约依赖」。
4. 接口签名以 [接口契约](Interfaces.md) 为准；本文档只描述「谁依赖谁、依赖什么、为何依赖」。

## 1 分层架构

SyncBox 采用单机多进程分层架构，进程包括 `queue-daemon`、`worker × N`、`client-A`、`client-B`、`admin-ui`。

```text
┌───────────────────────────────────────────────────────────────────────┐
│ L3 界面与运维层   M12 管理端只读接口      M13 进程编排与启停脚本          │
├───────────────────────────────────────────────────────────────────────┤
│ L2 传输与存储层   M10 对象存储与原子发布   M11 分片传输 worker 与断点续传 │
├───────────────────────────────────────────────────────────────────────┤
│ L1 业务能力层     M05 会话  M06 投递  M07 空间  M08 版本  M09 租约       │
├───────────────────────────────────────────────────────────────────────┤
│ L0 基座层         M01 公共契约  M02 队列内核  M03 守护进程  M04 审计      │
├───────────────────────────────────────────────────────────────────────┤
│ 横切质量层        M14 契约测试与 CI 门禁    M15 端到端验收与故障注入       │
└───────────────────────────────────────────────────────────────────────┘
```

**设计主线**：`M01`→`M02`→`M03` 构成必须先就位的「基座关键路径」；`M05`～`M09` 是互不改表的业务并行区；`M10`、`M11` 是与业务解耦的传输实现；`M12`、`M13` 只做装配与展示，不持有业务规则。

## 3 依赖关系（详细）

### 3.1 依赖总图

约定：`A ──► B` 表示 **B 依赖 A**（A 是上游/提供方，B 是下游/消费方）。

```text
M01 ──► M02 ──► M03 ──► M13
M01 ──► M04 ──► M05 ──► M06 ──► M12 ──► M13
M02 ──► M05, M06, M08, M09, M11, M12
M04 ──► M05, M06, M07, M08, M09, M11, M12
M07 ──► M08, M09
M09 ──► M08
M10 ──► M08, M11
M11 ──► M13
M02, M03, M06, M08, M11 ──► M15
M01 + 各模块对外接口 ──► M14
```

**依赖链（关键路径）**：

```text
M01 公共契约 ► M02 队列内核 ► M03 守护进程 ► M11 传输 worker ► M13 一键装配 ► M15 验收
```

`M02` 冻结得越早，`M05`～`M12` 越早能并行；这是全项目的**唯一硬阻塞点**。

### 3.4 启动与装配顺序

依赖决定了进程必须按下面顺序装配（由 M13 的启停脚本落实）：

1. **M02** 建库并创建受控目录：`init_database()` + `ensure_data_dirs()`。
2. **M03** 启动 `queue-daemon`，启动时执行一次 `recover()`。
3. **M05** 注入在线探针：`queue.set_online_probe(...)`；否则 M02 一律按离线分流。
4. **M06** 注册 `delay_expired` 钩子；**M09** 注册租约过期回收钩子（均经 `register_periodic_hook`）。
5. **M11** 启动 `worker × N`（用同一份 `visibility_timeout_ms` 配置）。
6. **M12 / client-A / client-B** 启动界面进程。

> ⚠️ 第 5 步的 `visibility_timeout_ms` 必须由 M02 的配置统一提供，daemon 与 worker 取同一份，否则会出现「任务比预期更早/更晚被回收」（见 `tests/acceptance/crash_recovery.md`）。

## 4 模块边界与解耦规则

1. **一表一主**：每张表只有一个负责人，只有他写这张表的 DDL 与 SQL；其他人一律通过对外接口访问，禁止「顺手查一下别人的表」。
2. **一接口一主**：每个对外接口只有一个负责人，签名、错误码与语义由他维护。
3. **只依赖接口，不依赖实现**：调用方只 import 接口模块，不得 import 对方的内部实现文件；每个模块必须能用 stub/mock 单独跑通自己的测试。
4. **禁止跨模块事务**：不允许 A 模块开事务、调用 B 模块写 C 表；需要同事务时显式传事务句柄（`audit.join_tx(tx)`）。
5. **接口先冻结后并行**：第 1 周内产出并打 `contract-v1` tag 的 `docs/Interfaces.md` 是唯一接口契约，此后任何变更双方 Review。
6. **目录即边界**：每个人只在自己负责的目录里改文件，跨目录改动走 PR 并通知对方。
7. **全局特例**：所有表的 DDL 由 M02 统一落库，但**表的写入权限仍归各模块**（见 Interfaces §6）；这是唯一一处「不是一表一主」的例外，由契约测试 C-10/C-13 强制。

## 8 风险与预案

| 风险 | 影响 | 预案 |
|---|---|---|
| M02 schema / `QueueAPI` 延迟 | 阻塞 M05～M12 全部下游 | D2 先冻结签名并交付 stub；M02 不承担 HTTP 与界面工作 |
| M04 `join_tx` 语义不统一 | 出现「业务成功但审计丢失」 | 契约测试 C-12 在第 2 周前拦住 |
| M10/M11 续传语义歧义 | 分片大小、`acked_bytes`、临时文件命名各说各话 | 冻结前 M02/M10/M11 三方一次谈清（见《契约修订提案》第 5 条） |
| 表结构被「顺手」改动 | 破坏一表一主 | DDL 只能由 M02 提交；结构变更走 ADR + C-13 |
| 跨模块事务 | 无法回滚的边界 | 禁止 A 开事务调 B 写 C 表，审计统一走 `join_tx` |
| 单点瓶颈 | 集成集中到一个人 | M14/M15 按模块与场景拆到四人，每人至少跑通一个验收场景 |
